# Ada-SPARK-Tim-Sort-Stub

Timsort as CPython's `listsort` runs it (Objects/listsort.txt), without galloping, on any `Value_Array` of up to `Max_Len = 10_000` integers with any `Positive` index range (`Input'Last < Positive'Last`). Runs are the longest ascending (`A (K) <= A (K + 1)`) or strictly descending stretch (reversed in place), extended to `Min_Run (N)` by binary insertion (after equal keys) and pushed on a run stack; after each push `merge_collapse` merges adjacent runs (with the corrected check of the third run from the top) and at the end the stack is merged down to one run. A merge copies the left run to a buffer and merges forward (`merge_lo`). Galloping (exponential search inside a merge) only changes how a merge copies, not which runs are merged, and is not done here. `Sort_Traced` also returns the event log (`Push (base, length)`, `Merge (stack position)`).

Proof (SPARK, `make prove`, level 2, cvc5 + z3, timeout 10 s, 720 checks; the same 720 with the Silver command at `--steps=1000000`): no run-time error (the stack holds at most one run per element; lengths and indices bounded by `Max_Len` and `Input'Last < Positive'Last`) and the Post: the result keeps the bounds, is sorted (pairwise `Sorted`) and is a permutation of the input (`Is_Perm`: every value occurs equally often, counted by `Occ`). Every run on the stack is sorted and the runs are contiguous from `Input'First` (`Stack_Ok`); count_run / reversal, binary insertion and the merge each prove sortedness of their range and leave the rest unchanged. For the counts, reversal and binary insertion move elements only by exchanges (`Swap`, the insertion moves the key down by adjacent exchanges, same result as shifting), the merge carries the buffer / right-run counts through its loop and closes with `Lemma_Occ_Shift` / `Lemma_Occ_Split` / `Lemma_Frame`, and `Sort_Traced` chains the counts over every call (`Same_Occ`, `Lemma_Same_Perm` gives the executable `Is_Perm`). No Assume / Annotate.

Run-length rule (H174): after every merge_collapse the whole stack satisfies `Runs_Rule` (spec): every run is longer than the next one and longer than the next two together, at every stack position, not only the top three. It is a proved `Loop_Invariant` of the run loop and a proved `Assert` after each collapse; inside the collapse loop the invariant is `Runs_Rule (Len, Top - 2)` (a merge only touches the top three runs), and the exit test, with the corrected check of the third run from the top (`Len (Idx - 2) <= Len (Idx - 1) + Len (Idx)`), closes the top. This is the invariant whose loss with a top-three-only check was the 2015 OpenJDK / CPython Timsort bug (de Gouw, Rot, de Boer, Bubel, Hähnle). The tests replay the stack from the event log and check the rule before every push, on de Gouw et al.'s example scaled by 2 (runs 240, 160, 50, 40, 60, then 35), where an own top-three-only model breaks it, and on 300 random inputs.

Tests: `tests.adb` (original) and `own_checks.adb` (seed 20261008): `Min_Run` against the listsort.txt values (63 -> 63, 64 -> 32, 65 -> 33, 2048 -> 32, 2112 -> 33) and an own model for N = 0 .. 70; the event log and result equal an own model of the listsort rules on random and duplicate-heavy inputs up to 5,000 values and on inputs built from natural runs; 4,100 random inputs of length 0 .. 40 plus edge cases against an insertion sort; `Is_Perm` against a sorted-copy comparison on all 7,381 pairs of length 0 .. 4 over -1 .. 1, and every `Sort` result `Is_Perm` of its input and equal to an insertion-sort reference on all arrays of length 0 .. 6 over -1 .. 1 at origins 1 and 7 and 2,000 random arrays (seed 20261009).
